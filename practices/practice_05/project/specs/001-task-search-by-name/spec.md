## User Scenarios & Testing *(mandatory)*

### User Story 1 - Найти задачу по названию (Priority: P1)

Пользователь открывает экран списка задач и использует поле поиска для быстрого нахождения существующей задачи по названию. Ввод выполняется с подсказкой; результаты обновляются без перезагрузки страницы, с учетом текущих фильтров/сортировки.

**Why this priority**: Поиск — основной способ навигации при большом количестве задач, снижает время на нахождение нужной задачи.

**Independent Test**: Ввести часть названия существующей задачи и убедиться, что соответствующие результаты отображаются, а несоответствующие скрываются.

**Acceptance Scenarios**:

1. Given список задач открыт, When пользователь вводит «репорт», Then в результате отображаются задачи, содержащие «репорт» в названии (без учета регистра), остальные скрыты.
2. Given введен запрос «fix», When удалить часть запроса до пустой строки, Then список возвращается к исходному состоянию без фильтра поиска без вызова поиска с пустым запросом.

---

### User Story 2 - Обработка пустых и отсутствующих результатов (Priority: P2)

Пользователь вводит запрос, по которому нет совпадений. Интерфейс явно сообщает, что ничего не найдено, и предлагает изменить запрос.

**Why this priority**: Ясная обратная связь предотвращает ощущение поломки и экономит время пользователя.

**Independent Test**: Ввести заведомо уникальную строку и проверить, что отображается пустое состояние с понятным текстом.

**Acceptance Scenarios**:

1. Given список задач открыт, When введен запрос «zzzzzz», Then отображается пустое состояние «Нет задач по запросу “zzzzzz”» и кнопка «Очистить поиск».
2. Given введен запрос длиннее 256 символов, When попытка выполнить поиск, Then показывается валидационная ошибка «Слишком длинный запрос» без выполнения запроса и с возможностью отредактировать строку.

---

### User Story 3 - Ошибки и повтор (Priority: P3)

При проблемах с загрузкой данных поиска пользователь видит компактное сообщение об ошибке и может повторить попытку.

**Why this priority**: Минимизирует фрустрацию и поддерживает устойчивость при сетевых сбоях.

**Independent Test**: Смоделировать отказ источника данных поиска; убедиться, что показывается сообщение с кнопкой «Повторить» и повтор работает.

**Acceptance Scenarios**:

1. Given недоступен источник задач, When введен запрос, Then отображается сообщение об ошибке с кнопкой «Повторить»; при повторе после восстановления данные появляются.

---

### Edge Cases

- Поиск по одной букве: отображение ограниченного количества результатов и/или подсказка «Уточните запрос».
- Пробелы в начале/конце: запрос триммится перед поиском; сравнение без учета регистра.
- Регистронезависимый поиск.
- Спецсимволы и экранирование: трактуются как обычные символы (не регулярные выражения).
- Длина запроса более 256 символов: подсветить ошибку валидации и не выполнять поиск.
- Большой список: отображение скелетонов/лоадеров при подзагрузке.
- Совместимость с активными фильтрами/сортировкой: поиск накладывается поверх, без сброса пользовательских настроек.

## Requirements *(mandatory)*

### Functional Requirements

- FR-001: Пользователь должен видеть поле поиска в верхней части экрана списка задач.
- FR-002: Ввод в поле поиска фильтрует список задач по подстроке в названии без учета регистра (только contains, режим exact отсутствует в v1).
- FR-003: Поиск обновляет результаты после короткой задержки ввода (debounce) без явного подтверждения.
- FR-004: При пустом поле поиска отображается полный исходный список с сохранением активных фильтров/сортировки; вызова поиска с пустым запросом не происходит.
- FR-005: Пустые результаты отображаются с текстом «Нет задач по запросу “{запрос}”» и кнопкой «Очистить поиск».
- FR-006: Состояние загрузки отображается индикатором (скелетон списка или спиннер в области результатов) во время запроса.
- FR-007: Ошибки отображаются в компактном блоке над списком с текстом «Не удалось выполнить поиск» и кнопкой «Повторить». Ошибка валидации слишком длинного запроса показывается отдельно от ошибок выполнения.
- FR-008: Кнопка «Очистить» в поле поиска очищает запрос и возвращает исходный список без вызова поиска с пустым запросом.
- FR-009: Поле поиска поддерживает клавишу Escape для очистки, Enter — не обязателен для запуска, но не должен ломать поведение.
- FR-010: Подсказка (placeholder) в поле: «Поиск по названию…».
- FR-011: Поиск не изменяет/сбрасывает активные фильтры/сортировку; применяется поверх них (включая все поддерживаемые фильтры в текущем UI).
- FR-012: Поиск работает при длине запроса от 1 до 256 символов после тримминга; пустая строка снимает фильтр и не инициирует запрос.
- FR-013: Запрос отображается в истории состояния экрана только локально, без навигационного редиректа.

### Key Entities

- Задача: атрибуты для отображения — id, title, status; поиск выполняется по title.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- SC-001: 95% поисковых запросов отображают результаты или пустое состояние менее чем за 1 секунду при стандартной нагрузке.
- SC-002: Пользователь находит нужную задачу по названию менее чем за 10 секунд в 90% случаев.
- SC-003: Не менее 90% пользователей завершают поиск без ошибок и повторов в стандартных условиях.
- SC-004: Активные фильтры/сортировка сохраняются при и после поиска в 100% случаев.

## Assumptions

- Пользователи работают в списке задач; переход на карточку задачи — существующая навигация.
- Источник данных поддерживает фильтрацию по подстроке названия.
- Подсветка совпадений в названии не обязательна для v1.
- Локализация интерфейса — русский язык.
