# Reconciliation: Task Search by Name/Title

Этот документ сверяет спецификации двух команд и фиксирует места согласия и расхождений. Исходные спецификации не изменялись и остаются источниками истины для своих областей до решения человеком.

## Conflict Resolution Options

1) Empty query: restore list vs invalid_query
- Option A: UI перехватывает пустой/пробельный ввод, не вызывает поиск и отображает исходный список (или вызывает существующий `list`). Consequence: логика неизменна; лишних round-trip нет; требуется UI-ветвление.
- Option B: API допускает пустой запрос как «снять фильтр/вернуть весь список». Consequence: проще UI; повышенная нагрузка и риск больших выборок; ослабление валидации.
- Option C: API сохраняет `invalid_query`, но возвращает хинт «используйте list»; UI по ошибке вызывает `list`. Consequence: дополнительный round-trip и сложнее маппинг.

2) Sorting: preserve current sorting vs id ascending
- Option A: API всегда сортирует по `id ASC`; UI пересортировывает в текущем пользовательском порядке. Consequence: минимальные изменения API; потребуются устойчивые ключи на UI.
- Option B: Расширить API параметром `sort` и поддержать порядок, выбранный UI. Consequence: больше работ по контракту; единообразие между клиентами.
- Option C: UI делает фильтрацию локально поверх уже отсортированного списка, избегая серверной сортировки. Consequence: может не масштабироваться, возможны расхождения с серверными данными.

3) Match mode: UI substring vs Logic contains|exact
- Option A: Сохранить `exact` в API, UI использует только `contains` в v1. Consequence: гибкость API без усложнения UX.
- Option B: Удалить `exact` из v1 и добавить позже. Consequence: упрощение сейчас, миграция позже.
- Option C: Добавить переключатель «точное совпадение» в UI. Consequence: усложнение UX, спорная ценность для v1.

4) Normalization: trim vs trim + collapse spaces
- Option A: Принять расширенную нормализацию API (trim + collapse + lowercase); UI для сообщений отображает исходный ввод пользователя, а не normalized_query. Consequence: меньше ложных промахов; возможна «магия» со сжатием пробелов.
- Option B: Ограничиться trim в API. Consequence: проще ментальная модель; больше промахов при «лишних» пробелах.
- Option C: Оставить расширенную нормализацию в API и возвращать meta (normalized_query, trimmed); UI может показывать подсказку «запрос нормализован». Consequence: прозрачность ценой дополнительного UI-текста.

5) Status/filter interaction
- Option A: UI передаёт только `status` в API; остальные активные фильтры применяет локально к результатам поиска. Consequence: минимальные изменения API; риск различий, если должны применяться другие серверные фильтры.
- Option B: Расширить API поддержкой всех актуальных фильтров списка (labels и пр.). Consequence: рост объёма работ, но единая серверная истинность.
- Option C: Делать `list` с фильтрами, затем локально фильтровать по подстроке без отдельного `search`. Consequence: упрощение API, но нагрузка на клиент и трафик.

6) Result shape and metadata
- Option A: Сохранить `SearchResult { items, meta }`; UI использует только `items`, meta — для телеметрии/диагностики. Consequence: универсальность; без ломки UI.
- Option B: Упростить до `Task[]` без meta. Consequence: потеря наблюдаемости и полезных сигналов.
- Option C: Сделать meta опциональной по флагу. Consequence: усложнение контракта, сомнительная польза.

7) UI loading/error states vs logic-level errors
- Option A: UI не посылает невалидные запросы (проверка на клиенте); любые сетевые/серверные ошибки маппит в компактное сообщение с «Повторить». Consequence: меньше «validation» ошибок в рантайме.
- Option B: UI показывает специфическое сообщение при `invalid_query` (валидация), и общее — при системных ошибках. Consequence: выше ясность для пользователя.

8) Query length limit (256)
- Option A: Лимит применяется только на API; UI может игнорировать, meta `trimmed=true` сигнализирует об усечении. Consequence: простота; возможна путаница в сообщении пользователю.
- Option B: UI также ограничивает длину ввода и предупреждает пользователя. Consequence: согласованность, чуть больше UI-работы.

9) Clear-search behavior
- Option A: UI по клику «Очистить» очищает поле и загружает исходный список через `list` (без вызова `search`). Consequence: согласование с `invalid_query` и отсутствие лишних запросов.
- Option B: UI вызывает `search` с пустой строкой, ловит `invalid_query` и затем вызывает `list`. Consequence: дополнительная задержка и сложность без пользы.

## Human Decisions Required

- Decision: Пустой запрос — восстановление списка или ошибка валидации?
  - Option A: UI локально восстанавливает список (не вызывает `search`).
  - Option B: API допускает пустой запрос как «весь список».
  - Recommendation from agent: Option A.
  - Impact on UI: Простая ветка очистки; без лишних запросов.
  - Impact on Logic: Контракт `invalid_query` остаётся неизменным.

- Decision: Сортировка результатов поиска.
  - Option A: API возвращает `id ASC`, UI пересортировывает по текущему выбору пользователя.
  - Option B: API принимает параметр `sort` и сортирует на сервере.
  - Recommendation from agent: Option A (минимальные изменения сейчас).
  - Impact on UI: Необходима клиентская сортировка набора.
  - Impact on Logic: Без изменений контракта или с минимальными.

- Decision: Экспонировать режим `exact` в v1?
  - Option A: Оставить в API, UI не показывает переключатель.
  - Option B: Удалить до v2.
  - Recommendation from agent: Option A.
  - Impact on UI: Без изменений UX.
  - Impact on Logic: Гибкий контракт сохраняется.

- Decision: Нормализация пробелов (collapse) в сравнении.
  - Option A: Принять collapse в API; UI отображает исходный ввод в сообщениях.
  - Option B: Оставить только trim.
  - Recommendation from agent: Option A.
  - Impact on UI: Возможна подсказка пользователю при нормализации.
  - Impact on Logic: Меньше промахов; стабильность сравнения.

- Decision: Как обрабатывать активные фильтры (кроме `status`).
  - Option A: Передавать только `status` в API; остальные фильтры применять в UI.
  - Option B: Расширить API, чтобы принимать все фильтры.
  - Recommendation from agent: Option A сейчас, B — позже при необходимости.
  - Impact on UI: Локальная фильтрация по меткам и т.п.
  - Impact on Logic: Без расширения контрактов в v1.

- Decision: Формат результата — нужна ли `meta` в контракте?
  - Option A: Оставить `meta`, UI может игнорировать.
  - Option B: Исключить `meta` и возвращать только `items`.
  - Recommendation from agent: Option A.
  - Impact on UI: Никаких обязательств; можно позже использовать.
  - Impact on Logic: Наблюдаемость и телеметрия сохраняются.

- Decision: Маппинг `invalid_query` на UI.
  - Option A: Предотвращать на клиенте и не вызывать API.
  - Option B: Показывать валидационное сообщение при ответе `invalid_query`.
  - Recommendation from agent: Option A (B как бэкап).
  - Impact on UI: Простая проверка длины и trim/пустоты.
  - Impact on Logic: Без изменений.

- Decision: Лимит длины запроса (256) — UI поддерживает или нет?
  - Option A: Только бэкендовый лимит, сигнализируемый через meta.
  - Option B: UI также ограничивает ввод и подсвечивает усечение.
  - Recommendation from agent: Option B, если реализация тривиальна.
  - Impact on UI: Небольшая валидация/подсказка.
  - Impact on Logic: Без изменений.

- Decision: Поведение «Очистить поиск».
  - Option A: Вызывать `list` и показывать исходный список без вызова `search`.
  - Option B: Пробовать `search` с пустым, затем `list` по ошибке.
  - Recommendation from agent: Option A.
  - Impact on UI: Быстрее и проще.
  - Impact on Logic: Контракт не меняется.

## Human Reconciliation — Approved

Решения ниже приняты человеком на основании предыдущей сверки. Агент не выбирал между конфликтующими вариантами. Обе исходные спецификации (UI и Logic) существовали до согласования и сохраняются как независимые документы. Production code до этого этапа не изменялся.

Утверждённые решения:
- Empty query: не отправляется в API; очистка поиска восстанавливает исходный список, сохраняя фильтры и сортировку; `invalid_query` для пустого ввода не является пользовательским сценарием.
- Matching: только contains; `exact` исключён из v1; регистронезависимый поиск.
- Normalization: trim + сравнение без учета регистра; collapse внутренних пробелов не обязателен; без regex/stemming/synonyms.
- Query length: максимум 256; превышение — явная validation error; правило согласовано на границе UI/Logic.
- Filters: поиск применяется поверх всех активных фильтров; поиск не сбрасывает фильтры; контракт не ограничивается только `status`.
- Sorting: поиск сохраняет существующую сортировку списка; API не навязывает `id ascending`; без нового параметра `sort` специально под поиск.
- Result shape: минимально — Task { id, title, status }; metadata не обязательна в v1.
- Error mapping: UI показывает понятное сообщение и retry; валидировать слишком длинный запрос отдельно от обычных ошибок; пустой query не попадает в API; без лишних типов ошибок.
- Clear search: кнопка очистки и Esc очищают query и восстанавливают список без вызова поиска с пустым запросом; фильтры/сортировка сохраняются.
