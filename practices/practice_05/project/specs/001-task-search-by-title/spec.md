## User Scenarios & Testing (mandatory)

### User Story 1 - Найти задачу по подстроке названия (Priority: P1)

Пользователь хочет быстро найти уже существующую задачу, помня полное или частичное название.

**Why this priority**: Это основной сценарий использования поиска; обеспечивает быстрый доступ к нужной задаче.

**Independent Test**: При наличии задачи с заголовком "Fix login", запрос "Fix login" возвращает эту задачу; при запросе "login" возвращаются все задачи, содержащие "login".

**Acceptance Scenarios**:

1. Given в хранилище есть задача с названием "Fix login", When выполняется поиск по запросу "Fix login", Then результат содержит эту задачу с корректными id и status.
2. Given в хранилище нет задач с совпадением по подстроке, When выполняется поиск по запросу, Then результат пуст и это успешный ответ без ошибок.

---

### User Story 2 - Частичный поиск (Priority: P2)

Пользователь помнит только часть названия задачи и хочет найти подходящие варианты.

**Why this priority**: Частичный поиск повышает находчивость и снижает зависимость от точного ввода.

**Independent Test**: При запросе "login" возвращаются все задачи, в названии которых встречается "login".

**Acceptance Scenarios**:

1. Given в хранилище есть задачи "Fix login", "Improve login UX", When поиск по запросу "login", Then возвращаются обе задачи; порядок результатов не должен менять текущую сортировку списка.

---

### User Story 3 - Поиск без учета регистра (Priority: P2)

Пользователь может вводить запрос в любом регистре; сравнение выполняется без учета регистра. Лишние пробелы по краям не влияют на сравнение (trim).

**Why this priority**: Снижает количество ложных промахов из‑за форматирования и регистра.

**Independent Test**: Запросы "  LOGIN  ", "login" и "LoGiN" ведут к одинаковому результату.

**Acceptance Scenarios**:

1. Given в хранилище есть задача "Fix Login", When запрос "  login  ", Then задача находится.
2. Given задача "Add LOGOUT", When запрос "login", Then задача не находится (строгое частичное соответствие по подстроке без стемминга).

---

### User Story 4 - Обработка пустого и слишком длинного запроса (Priority: P3)

Пустой или пробельный запрос не является поисковым запросом для API в v1. Слишком длинный запрос должен валидироваться.

**Why this priority**: Предотвращает неожиданно большие результаты и лишнюю нагрузку.

**Independent Test**: Пустой запрос не отправляется в API; запрос длиннее 256 символов приводит к валидационной ошибке.

**Acceptance Scenarios**:

1. Given пустой/пробельный запрос, When инициируется поиск, Then такой запрос не должен отправляться в API.
2. Given запрос длиной > 256 символов, When поиск, Then возвращается валидационная ошибка о превышении максимальной длины.

---

### Edge Cases

- Очень длинный запрос (>256): вернуть валидационную ошибку, поиск не выполняется.
- Наличие невидимых символов (табуляции, неразрывные пробелы): рассматриваются как обычные символы; сравнение регистронезависимое; пробелы по краям убираются (trim); схлопывание внутренних пробелов не является обязательным.
- Дубликаты названий задач: возвращать все совпадения; логика поиска не должна менять текущую сортировку списка.
- Нулевое число задач в системе: корректно возвращать пустой результат.
- Спецсимволы в запросе: трактовать как литералы, не как регулярные выражения.

## Requirements (mandatory)

### Functional Requirements

- FR-001: Система MUST принимать строковый запрос пользователя для поиска по названию существующих задач (после trim длиной 1..256 символов).
- FR-002: Система MUST нормализовать сравнение: trim по краям и регистронезависимое сопоставление; схлопывание внутренних пробелов не обязательно.
- FR-003: Система MUST поддерживать только подстрочное сопоставление (contains) в v1.
- FR-004: Система MUST возвращать сведения по каждой найденной задаче: id, title (исходный), status.
- FR-005: Система MUST валидировать длину запроса: >256 символов — валидационная ошибка; поиск не выполняется.
- FR-006: Система MUST трактовать спецсимволы как обычные символы (без интерпретации как паттернов).
- FR-007: Система MUST не выполнять стемминг/лемматизацию в v1; сравнение только по подстроке без учета регистра.
- FR-008: Система MUST выполнять поиск поверх активных фильтров вызывающей стороны; контракт поиска не ограничивается единственным фильтром `status` и не сбрасывает уже применённые фильтры.
- FR-009: Система MUST не изменять текущую сортировку списка; поиск не навязывает порядок `id ascending` и не вводит новый параметр `sort` в v1.

### Обзор логики поиска (суммарно)

- Входные данные: строка запроса `query` после trim длиной 1..256.
- Алгоритм поиска: trim → приведение к одному регистру для сравнения → применение активных фильтров контекста → сравнение подстроки без учёта регистра → вернуть без изменения порядка, принятого в текущем листинге.
- Правила сравнения: литеральное сопоставление подстроки; без регекспов/стемминга/синонимов.
- Регистр: сравнение регистронезависимое.
- Пустой запрос: не является поисковым запросом для API в v1 (клиенты не должны вызывать поиск с пустым query).
- Формат результата: массив `Task[]` с полями `id`, `title`, `status`.
- Ошибки: валидационная ошибка при превышении максимальной длины запроса; прочие системные ошибки маппятся вызывающей стороной согласно её политике.
- Существующие API/CLI: поиск добавляется как новый контракт, не меняя `list`, `add`, `done`, `reopen`, `clear`.
- Обратная совместимость: новая операция не меняет поведение существующих команд; формат хранилища задач не меняется; поиск не меняет сортировку списка.

### Key Entities

- Task: { id: integer, title: string, status: "open"|"done" }
- SearchRequest v1: { query: string } (после trim длиной 1..256; фильтры и сортировка наследуются от контекста листинга; новый параметр `sort` не вводится).
- SearchResponse v1: Task[]

## Success Criteria (mandatory)

### Measurable Outcomes

- SC-001: 95% поисковых запросов с корректным вводом возвращают результаты менее чем за 1 секунду на типичном наборе до 5 000 задач.
- SC-002: Валидация слишком длинного запроса срабатывает в 100% случаев без падений; пустые/пробельные запросы не доходят до API согласно контракту.
- SC-003: Пользователи успешно находят нужную задачу по части названия в 90% случаев в UX‑тестах на репрезентативном датасете.

## Assumptions

- Поиск ограничивается названием задачи; по описанию/тегам поиск не входит в v1.
- Длина названия задач ограничена существующей моделью; запрос обрезаем до 256 символов для сравнения.
- По умолчанию используется подстрочное сравнение после нормализации регистра и пробелов.
- Порядок результатов по id соответствует текущей практике листинга задач в системе.
