# Рефлексия

## Что было сделано
- Изучен проект `practices/practice_05/project/`: CLI-трекер задач на Python, тесты на pytest, GUI-обёртка.
- Выбран сценарий «поиск задач по названию» как пересечение UI/логики.
- Проанализированы реализация `src/task_cli.py` (подкоманда `search`), контрактные тесты `tests/contract/test_search_cli.py`, UI/Logic спеки и документы согласования (`COMMON_CONTRACT.md`, `RECONCILIATION.md`).
- Сопоставлены два SDD-подхода: OpenSpec и Speckit (Specify) на основе артефактов проекта.
- Подготовлены сравнение и выводы без изменения исходного кода.

## Что согласовали между UI и логикой
- Поиск только по названию (title), режим contains, регистронезависимый, trim по краям.
- Пустой запрос не отправляется в API; очистка возвращает исходный список, сохраняя фильтры/сортировку.
- Максимальная длина запроса — 256 символов; превышение — валидационная ошибка.
- Поиск применяется поверх активных фильтров; сортировка результатов не меняется API (UI сохраняет текущую).
- Формат результата: список задач с полями `id`, `title`, `status`; metadata в v1 не обязательна.

См. фиксацию в `specs/.../COMMON_CONTRACT.md` и итоговую секцию «Human Reconciliation — Approved» в `RECONCILIATION.md`.

## Какие неоднозначности обнаружили
- Пустой запрос: ошибка валидации на логике против «восстановить список» на UI. Решение: UI не вызывает поисковый API при пустом вводе.
- Сортировка: логика предлагала `id ASC`, UI — «сохранять текущую». Решение: API не навязывает сортировку; UI контролирует отображение.
- Режим `exact`: присутствовал в черновике логики, но исключён из v1 общего контракта.
- Нормализация пробелов: логика предлагала схлопывание; итог — только trim, без collapse в v1.

## Что удалось выявить до кода
- Необходимость валидации длины запроса и поведения пустого запроса была зафиксирована в спецификациях до реализации, что позволило избежать неопределённости на этапе UI и тестов.
- Влияние сортировки и фильтров на результаты поиска: закреплено в контракте, предотвращая регресс в UX.

## Что показал OpenSpec
- Сильный этап «sync/archive» и явные роли: после приёмки можно зафиксировать изменения и их контекст в `openspec/changes/archive/*` и `openspec/specs/*`.
- Подходит для документирования принятых решений и истории изменений, что критично для контроля качества в brownfield.

## Что показал второй SDD-подход
- Speckit (Specify) дал чёткий цикл `spec → plan → tasks → implement` с ревью-гейтами, что удобно для согласования UI и логики до реализации.
- Шаблоны и workflows в `.specify/*` позволили сформировать согласованный контракт (`COMMON_CONTRACT.md`) и сверку (`RECONCILIATION.md`).

## Что оказалось сложнее, чем ожидалось
- Совмещение двух подходов требует дисциплины, чтобы не допустить расхождений: одинаковые решения должны присутствовать в обеих системах (Speckit-спеки и OpenSpec-артефакты).
- Тонкие детали нормализации и сортировки легко ускользают без контрактных тестов; потребовалась явная фиксация.

## Что было полезно
- Разделение «UI-спецификация» и «Logic-спецификация» с последующей сверкой выявило конфликтные места до кода.
- Контрактные тесты `tests/contract/test_search_cli.py` обеспечили проверяемость ключевых требований: contains, trim, регистронезависимость, лимит длины, фильтр по статусу.
- Использование CLI как единого источника правды для GUI снизило риск расхождений.

## Чему научились
- Утверждать общий контракт до реализации снижает расходы на переделку и споры на этапе UI/логики.
- Для brownfield-проектов важно отделять артефакты спецификаций от кода и иметь трассируемость решений.
- Связка: Speckit для раннего согласования, OpenSpec для приёмки/архива — работает на практике и даёт прозрачность.

## Итог
- На исследованном сценарии поиск по названию реализуем и проверяем через чётко согласованный контракт.
- Speckit удобен на этапе согласования и планирования, OpenSpec — на этапе приёмки и поддержания актуальности артефактов.
- В результате спецификации и тесты описывают поведение до и после реализации без необходимости модифицировать код в рамках этой практики.
