# Сравнение SDD-фреймворков

## 1. Контекст проекта
- Проект: минимальный трекер задач на Python (CLI), с простой Tkinter-обёрткой.
- Стек: Python 3, argparse, JSON как локальное хранилище; тесты на pytest; сценарные проверки через `scripts/check.sh`.
- Архитектура: один файл `src/task_cli.py` объединяет хранилище, операции и CLI; GUI вызывает CLI через subprocess. Данные — `data/tasks.json`.
- Исследованный сценарий: поиск задач по подстроке названия (CLI-команда `search`).
- Почему подходит: сценарий пересекает UI и логику, требует явного контракта (валидация, нормализация, фильтры/сортировка), имеет контрактные тесты и обе спецификации (UI и Logic) с актом согласования.

Основные артефакты по сценарию:
- Реализация: `src/task_cli.py` (подкоманда `search`, валидация 1..256, фильтрация по статусу, вывод в формате списка).
- Тесты: `tests/contract/test_search_cli.py` (проверяют contains, регистронезависимость, trim, лимит длины, фильтр по статусу).
- UI-спецификация: `project/specs/001-task-search-by-name/spec.md`.
- Logic-спецификация: `project/specs/001-task-search-by-title/spec.md`.
- Общий контракт и сверка: `project/specs/001-task-search-by-name/COMMON_CONTRACT.md`, `RECONCILIATION.md`.

## 2. Выбранный SDD-фреймворк
- Название: Speckit (Specify workflow; каталожная папка `.specify/`).
- Почему выбран:
  - Уже интегрирован в проект: `.specify/workflows/speckit/workflow.yml`, `.specify/integration.json`, `.specify/templates/*`, bash-скрипты.
  - Поддерживает явный workflow: `specify → plan → tasks → implement` с gate-review шагами.
  - Интегрируется с различными бэкендами (включая `opencode`) и даёт артефакты до кода.
- Релевантные механизмы:
  - Inputs и steps с ревью-гейтами (`review-spec`, `review-plan`).
  - Шаблоны артефактов и генерация с фиксацией фичи в `specs/<feature>/`.
  - Интеграция-интерпретатор (integration: opencode) для единообразных команд.

## 3. OpenSpec
- Workflow (согласно контексту практики и артефактам репозитория): `Explore → propose → human review → apply → tests/acceptance → sync/archive`.
- Артефакты: `openspec/specs/*` (specs), `openspec/changes/archive/*` (архив изменений), `openspec/config.yaml` (правила), навыки `.opencode/skills/openspec-*` (propose/apply/sync/archive/explore).
- Роли:
  - Человек: задаёт цель, фиксирует границы, принимает решения на ревью.
  - Модель: пишет текст (спеки/планы) и код по согласованному контракту.
  - CLI/runner: выполняет детерминированные операции (применение, проверки, синхронизация/архивация).
- Review: явно присутствует (human review) перед apply.
- Проверки: контрактные тесты (`tests/contract/test_search_cli.py`) и базовые pytest; возможен автозапуск через `.opencode/plugins/auto-check.js`.
- Sync/Archive: `openspec/changes/archive/*` фиксирует принятую реализацию; `openspec/specs/*` — текущие спецификации.

## 4. Сравнение

| Критерий | OpenSpec | Speckit (Specify) | Наблюдение на проекте |
| --- | --- | --- | --- |
| 1. Формулировка задачи | propose с явной границей изменения, контекст в `openspec/config.yaml` | `specify` с входным описанием (`inputs.spec`) | Поиск описан в UI/Logic спеках, плюс в Speckit feature указатель `.specify/feature.json` → `specs/001-task-search-by-title` |
| 2. Артефакты до кода | proposals/specs в `openspec/specs/*`, archive | `spec`, `plan`, `tasks` по шаблонам `.specify/templates/*` | В проекте есть двойной набор: `openspec/specs/*` и `specs/001-*/` с планами/чеклистами |
| 3. Описание требований | Требования фиксируются в spec и чеклистах; роль человека — ограничить область | Speckit `spec` и чеклисты; гейт на ревью | `specs/001-task-search-by-name/spec.md` и `.../by-title/spec.md` содержат FR/edge cases |
| 4. Описание design/решения | Проектные решения в spec/plan; код следует после review | Plan/Tasks до implement | В `.../COMMON_CONTRACT.md` и `RECONCILIATION.md` зафиксированы решения до реализации |
| 5. Границы изменения | Explore/propose явно оговаривают scope | Шаг `specify` задаёт scope фичи | Поиск не меняет формат хранилища и существующие команды (см. спецификации) |
| 6. Human review | Обязателен перед apply | Gate steps `review-spec`, `review-plan` | Присутствуют reconciliation/human decisions документами |
| 7. Переход к реализации | `apply` после согласования; CLI выполняет детерминированно | `implement` шаг, интеграция выполняет | Фича реализована в `src/task_cli.py` как подкоманда `search` |
| 8. Проверка соответствия | Tests/acceptance включены в цикл (pytest/contract) | Проверки запускаются runner’ом интеграции | Тест `tests/contract/test_search_cli.py` проверяет контракт contains/trim/case-insensitive/len |
| 9. Новые факты/изменения | sync/archive обновляют спеки и журнал | план/задачи пересобираются; ревью снова | В проекте есть archive записей и уточнения в `RECONCILIATION.md` |
| 10. Актуальность спецификаций | Sync поддерживает согласованность | Templates и gate-процесс требуют обновления | Спеки и договор зафиксированы; CLI соответствует тестам |
| 11. Роль человека | Формулирует цель, принимает решения | Точки-гейты для утверждения | Human-approved решения перечислены в `COMMON_CONTRACT.md` |
| 12. Роль AI-агента | Пишет текст/код, исполняет под контролем CLI | Генерирует `spec/plan/tasks`, далее implement | В проекте упоминание `.opencode/skills/openspec-*`; Speckit использует integration opencode |
| 13. Что делает CLI/tooling vs модель | CLI применяет, архивирует, гоняет тесты; модель пишет | Speckit orchestrator вызывает integration-команды | `.specify/integration.json` указывает `opencode` как integration; единый раннер |
| 14. Удобство для brownfield | Высокое: можно завести спеки/changes без ломки кода | Высокое: workflow поверх существующего кода | Пример: добавление `search` без изменения формата данных и существующих команд |
| 15. Встраивание в репозиторий | Папки `openspec/*`, `.opencode/*` | Папка `.specify/*`, `specs/*` | Обе системы сосуществуют, используют одни и те же фичи |
| 16. Плюсы/минусы на этом проекте | Сильная дисциплина sync/archive; явные роли | Быстрый луп spec→plan→tasks, встроенные гейты | На практике: удобнее применять Speckit для черновиков, OpenSpec — для приёмки и архива |

Привязка к коду/тестам: реализация `search` в `src/task_cli.py` точно следует согласованному контракту (нормализация, лимиты, фильтры), что отражено тестом `tests/contract/test_search_cli.py` и документами `COMMON_CONTRACT.md` и `RECONCILIATION.md`.

## 5. Brownfield-анализ
- Проект изначально CLI-ориентирован; добавление поиска — точечная подкоманда, не нарушающая формат данных и существующие операции (`add`, `list`, `done`, `reopen`, `clear`).
- UI (Tkinter) использует CLI как источник правды, что сокращает риск расхождений; поисковое поведение на UI согласовано с логикой до кода и реализовано без ломки существующих сценариев (очистка, retry, empty).
- Оба подхода (OpenSpec и Speckit) применяются поверх существующего кода: спеки, ревью, артефакты и проверки живут отдельно от исходников, что удобно для brownfield.

## 6. Сильные стороны OpenSpec
- Жёсткий цикл sync/archive и дисциплина артефактов.
- Явное разделение ролей (human/model/CLI) с фокусом на приёмку и архивацию изменений.
- Хорошо подходит для фиксации «как сделано» и аудита.

## 7. Сильные стороны Speckit (Specify)
- Ориентация на ранние артефакты: `spec → plan → tasks` с гейтами ревью.
- Удобная оркестрация через integration (в проекте — `opencode`), единый раннер и шаблоны.
- Быстрое прототипирование и согласование до реализации, особенно для новых фич внутри существующего кода.

## 8. Недостатки и trade-offs
- OpenSpec: более тяжёлый финальный цикл (sync/archive), может быть избыточен для мелких правок, но полезен для контроля изменений и аудита.
- Speckit: без жёсткого sync может «расползаться» актуальность документов, если не зафиксировать принятую реализацию; требует дисциплины при переносе в прод.
- Совместное использование: важно не дублировать и не рассинхронизировать спеки; в проекте это решено через `RECONCILIATION.md` и общий контракт.

## 9. Итоговый вывод
- Для согласования и быстрых изменений в brownfield-проекте удобнее Speckit: он структурирует доводку требований и плана до кода, с явными гейтами.
- Для приёмки, фиксации и долгосрочной актуальности артефактов предпочтительнее OpenSpec: цикл sync/archive и роли обеспечивают прозрачность и трассируемость.
- На этом проекте связка «Speckit для предварительных артефактов → OpenSpec для приёмки и архива» показала естественное разделение ответственности и снижает регрессии: контракт `search` согласован до кода и подтверждён контрактными тестами.
