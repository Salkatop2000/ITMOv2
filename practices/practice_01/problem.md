# Проблема и метрики

Файл ведёт OpenCode. Обсудите с агентом содержание и проверьте предложенный diff. Все дополнения и исправления поручайте агенту в чате.

## Проблема

- Пользователь: в предоставленных материалах не указан (требует уточнения).
- Ситуация: реализован обработчик `POST /api/reviews`, принимающий тело запроса как `dict`.
- Что происходит сейчас: в обработчике выполняется доступ `payload["diff"]` без проверки наличия ключа; при отсутствии ключа это статически указывает на возможность `KeyError`. Фактический HTTP-статус в этом случае diff не подтверждает. Метод `ReviewService.review` формирует промпт и синхронно вызывает `LLM.generate`.
- Почему это мешает пользователю или бизнесу: отсутствие валидации входных данных создаёт риск необработанных исключений и неопределённого поведения API при некорректном теле запроса; требуются явные правила валидации и обработки ошибок.
- Что не входит в задачу: полноценный рефакторинг на Pydantic, асинхронные очереди и продвинутые механизмы защиты — запланировано как последующие инкременты.

## Метрики

В этом разделе разделены подтверждённые наблюдения (AS IS), способы проверки и предлагаемые цели (TO BE). Цели помечены как требующие согласования и не содержат неподтверждённых чисел.

### AS IS: подтверждённые наблюдения и источники

- Ошибка при отсутствии `diff`:
  Статически возможен `KeyError` из-за доступа `payload["diff"]` без проверки; фактический HTTP-статус неизвестен.
  Источники: TRAINING_PR.diff (app/api.py:35–37), adr.md, tests_integration.md.

- Обработка некорректного входа:
  Явной схемы запроса/ответа нет; поведение при неверном типе/контент-тайпе неизвестно.
  Источники: TRAINING_PR.diff (app/api.py:35–37), отсутствие Pydantic-моделей; analysis.md.

- Время обработки большого diff:
  Вызов `LLM.generate` синхронный; таймауты/лимиты не показаны; фактическая латентность не определена источниками.
  Источники: TRAINING_PR.diff (app/review_service.py:19–22), tests_load.md.

- Обработка исключения `LLM.generate`:
  Исключения не оборачиваются; результат на уровне API неизвестен.
  Источники: TRAINING_PR.diff (app/review_service.py:19–22; app/api.py:35–37), adr.md, tests_integration.md.

### Как измеряем (будущие проверки)

- Ошибка при отсутствии `diff`:
  Интеграционный тест POST `/api/reviews` с телом `{}`; зафиксировать статус и тело ответа. Статическая проверка подтверждает риск `KeyError`.

- Обработка некорректного входа:
  Набор интеграционных тестов: не-JSON, неверный `Content-Type`, JSON с неверным типом поля `diff`; зафиксировать статусы и сообщения об ошибке.

- Время обработки большого diff:
  Нагрузочные тесты: согласовать диапазон размеров диффа; измерять p50/p95 latency с заглушкой/моком LLM, задающим задержку.

- Обработка исключения `LLM.generate`:
  Интеграционный тест с мок-LLM, выбрасывающим исключение; проверить, что ответ контролируемый и без трассировки.

### TO BE: цели (требуют согласования)

- Ошибка при отсутствии `diff`:
  Явная валидация входа и возврат клиентской ошибки с описанием отсутствующего поля. Статус-код согласовать.

- Обработка некорректного входа:
  Ввести схему запроса; при несоответствии — предсказуемая клиентская ошибка. Статусы и формат ошибки согласовать.

- Время обработки большого diff:
  Определить цели по задержке и лимиты размера/таймаута, совместимые с дальнейшими тестами. Конкретные пороги согласовать.

- Обработка исключения `LLM.generate`:
  Контролируемый ответ сервиса без трассировки стека. Конкретная стратегия и статус-коды согласовать.

### Неизвестно/требует согласования

- Роль пользователя сервиса.
- Точные статус-коды и формат ошибок для клиентских случаев.
- Диапазон «больших» diff, пороги задержки и SLA.
- Требования к Content-Type, типу и максимальному размеру поля `diff`.

## Почему изменение метрики подтвердит решение проблемы

Снижение доли ошибок сервера за счёт валидации входа и предсказуемая клиентская ошибка при некорректном входе демонстрируют, что ошибки пользователя не приводят к падению сервиса. Ограничение времени и размера позволит удерживать задержки в согласованных пределах. Контролируемая обработка исключений LLM повысит надёжность интеграции.
